# Адаптивные блокировки диапазонов

Текущий benchmark по умолчанию использует реализацию модели из статьи: **квантильный balanced** и **точный DP со штрафом за пересечения границ**, ускоренный через CHT. Число блокировок фиксировано, границы защищаемых областей меняются по статистике запросов. Код — [PaperRangeLock](dynamic/paper_lock.hpp) и [построители разбиения](dynamic/paper_partitioner.hpp).

Полный локальный снимок до изменений хранится на исходной машине в `snapshots/2026-11-17-before-paper/workspace.tar.gz` вместе с манифестом SHA-256. Для запуска на другой машине достаточно клонировать эту ветку и собрать проект по инструкции ниже.

Старые классы `DynamicLock` и генетический поиск доступны через `--model legacy`. Для воспроизведения прежнего тела запроса также нужен `--write-body single`. Старые таблицы и графики не являются результатами новой модели: она использует другую целевую функцию и по умолчанию изменяет весь диапазон.

## Модель из статьи

Для выбранных статистикой запросов с первым и последним мелкими блоками `a(q), b(q)` считаются:

```text
h[i] = число запросов, для которых a(q) ≤ i ≤ b(q)
c[i] = число запросов, для которых a(q) < i ≤ b(q); c[0] = 0
H(a,b) = h[a] + ... + h[b−1]
Φ(P) = Σj H(p[j],p[j+1])² + λ Σj=1..K−1 c[p[j]]
```

Первое слагаемое штрафует концентрацию нагрузки на одной группе. Второе учитывает дополнительные захваты mutex: запрос захватывает одну блокировку плюс по одной на каждую пересечённую выбранную границу. Это модель для выбора разбиения, а не гарантия минимума времени исполнения.

- **Balanced:** внутренний разрез `j` — первая допустимая позиция `r` с `K·S(r) ≥ j·S(B)`, где `S` — префиксные суммы `h`. Сканирование идёт от предыдущего разреза вперёд, оставляя хотя бы один блок каждой последующей группе. Время `O(B+K)`. Это квантильное правило статьи, а не прежний минимакс из `DynamicLock`.
- **DynamicProgramming:** точный минимум `Φ` по непустым последовательным группам. Рекуррентность `D[k,r] = min_l {D[k−1,l] + (S[r]−S[l])² + λc[l]}` вычисляется монотонным CHT за `O(KB)`. Предки для восстановления границ занимают `O(KB)` памяти. Вычисление целочисленное; при превышении проверенного диапазона стоимости выбрасывается исключение вместо переполнения.

В обеих стратегиях кандидат публикуется только при снижении **полной** `Φ` больше заданного порога. Малой выборке дают накопиться. Дополнительных эвристик под конкретный сценарий нет; одинаковые настройки используются в проверочной серии.

| Настройка | По умолчанию | Смысл |
|---|---:|---|
| `K` | 64 в benchmark | Фиксированное число mutex, параметр шаблона |
| `bins` / `--bins` | 1024 | Запрошенное число мелких блоков |
| `sample_rate` / `--sample-rate` | 64 | Псевдослучайная выборка примерно одного запроса из 64 |
| `lambda` / `--lambda` | 10000 | Вес штрафа за пересечение границы |
| `minimum_samples` / `--min-samples` | 640 | Минимум выбранных запросов перед оптимизацией |
| `minimum_improvement` / `--min-improvement` | 0.10 | Требуемое относительное снижение `Φ` |
| `StartRebuilder` / `--rebuild-ms` | 30 с / 30000 мс | Пауза перед следующей проверкой; не длительность перестройки |

`λ` применяется к **сырым счётчикам**, без скрытой нормировки. Его эффективный вес зависит от числа наблюдений в статистическом окне. В статье использовано `10⁷`; этот режим доступен через `--lambda 10000000`. В локальном коротком пилоте он подавлял полезное дробление, поэтому рабочее значение `10⁴` выбрано на пилоте и зафиксировано перед отдельной проверочной серией. Формула не менялась. [Все пилотные настройки и команды](BENCHMARK_RESULT/2026-11-17/paper_pilot/manifest.json), включая проигрыши при `10⁷`, сохранены.

Размер мелкого блока — `ceil(n / min(n,bins))`, последний блок может быть короче. Поэтому фактическое число блоков иногда меньше запрошенного; его сообщает `GetBinCount()` и CSV `actual_bins`. Для основных степеней двойки `n=2²⁰/2²⁶`, `B=1024` фактическое число равно 1024, а начальное разбиение совпадает с равномерным fixed.

## Статистика и безопасная публикация

После проверки версии запроса выборка обновляет атомарные `h[i]`, `c[i]` и счётчик начал в первом блоке запроса. При эксклюзивном захвате используется состояние псевдослучайного генератора в первой уже захваченной блокировке; это убирает обращение к TLS на каждом запросе. Настоящие shared-чтения используют состояние генератора, локальное для потока, поскольку читатели могут одновременно владеть одним read-lock. Сами счётчики остаются атомарными во всех вариантах; глобального счётчика на каждом запросе нет. Частота `1/64` — случайная выборка запросов, а не синхронный выбор каждого 64-го запроса всех потоков. Формула стоимости и вероятность выборки от этой оптимизации не меняются.

Перестройщик читает счётчики relaxed-load операциями, не останавливая запросы. Он использует разность с предыдущим обработанным снимком; недостаточная выборка продолжает накапливаться. Это приближённый профиль: отдельные приращения одного запроса могут попасть в соседние статистические окна. Согласованное мгновенное состояние всех счётчиков не предполагается.

Вычисление кандидата выполняется вне блокировок данных. Для публикации закрывается admission, затем захватываются все `K` mutex по возрастанию. Уже допущенные запросы могут закончиться; новые ждут. После захвата всех mutex epoch переводится в нечётное значение, заменяются границы и атомарная таблица отображения, статистика сбрасывается, epoch становится следующим чётным. Затем mutex освобождаются и admission открывается. Запрос повторно проверяет epoch после захвата своего диапазона mutex; устаревшее отображение приводит к освобождению и повторной попытке.

`SnapshotStatistics()` — отдельный **согласованный диагностический** снимок: он останавливает admission и захватывает все mutex. Оптимизация этот метод не вызывает. Исключение в фоновом перестройщике сохраняется и останавливает его; `RethrowBackgroundError()` повторно выбрасывает сохранённую ошибку. Benchmark проверяет её после `StopRebuilder()`. Ошибка сохраняется в объекте и при последующем перезапуске потока.

## API текущей реализации

```cpp
#include "dynamic/paper_lock.hpp"
#include <vector>

std::vector<uint64_t> data(1 << 20);
PaperLockConfig config;
config.bins = 1024;
config.sample_rate = 64;
config.lambda = 10000;
PaperRangeLock<64> lock(data.size(), config, PaperStrategy::DynamicProgramming);
lock.StartRebuilder(); // Проверка раз в 30 секунд, запуск явный.
lock.WriteQuery(10, 20, [&](size_t left, size_t right) {
    for (size_t i = left; i <= right; ++i) ++data[i];
});
lock.StopRebuilder();
lock.RethrowBackgroundError();
```

`PaperStrategy::Balanced` выбирает квантильное разбиение. `WriteQuery` и `ReadQuery` работают с **включённым** диапазоном `[left,right]`; точка — `[i,i]`. Концы ограничиваются размером массива и упорядочиваются, для пустого массива callback не вызывается. Данные принадлежат вызывающему коду. Callback должен завершить обращения до возврата; из него нельзя вызывать методы того же объекта блокировки. Все конкурирующие обращения к массиву должны соблюдать этот протокол.

Второй параметр шаблона выбирает тип блокировок, например `PaperRangeLock<64,std::shared_mutex>`. Тогда `ReadQuery` берёт shared/read-lock, а `WriteQuery` и публикация — exclusive/write-lock. С `std::mutex` и `spinlock` оба типа запросов захватываются эксклюзивно. `PartitionCuts()` возвращает границы в координатах элементов; группы представлены полуоткрытыми интервалами между соседними границами.

## Запуск и честное измерение

Текущие значения по умолчанию — **`--model paper --write-body range`**. Каждый пишущий запрос увеличивает **все элементы диапазона на 1**, как в статье. Читающий запрос суммирует диапазон без изменения данных. `--read-percent` задаёт долю чтений, `--point-percent` — долю точечных запросов внутри того же сценария. Для них используются отдельные генераторы; CSV сохраняет фактическое число чтений, записей, точек и диапазонов.

```sh
./build/paper-release/adaptive_lock_benchmark \
  --model paper --write-body range --scenario steady_range \
  --threads 8 --array-size 67108864 --hot-width 4194304 --range-length 10000 \
  --operations 64000000 --bins 1024 --lambda 10000 \
  --sample-rate 64 --rebuild-ms 30000 --repetitions 3 --seed 97 \
  --implementations fixed,balanced,dynamic_dp --csv /tmp/paper-steady.csv
```

`--operations` — **суммарное** число запросов по всем потокам для одной реализации в одном повторе. Трассы потоков генерируются заранее и циклически повторяются; `--trace-size` ограничивает суммарное число сохранённых запросов на фазу. Смена фазы следует за числом выполненных операций, а не таймером; быстрые и медленные варианты достигают её в разное время.

Полное `wall_s` включает создание структуры, холодное начало, статистику, потоки, все перестройки и уничтожение. Генерация входа, обнуление данных и проверка результата вынесены за таймер одинаково. Каждое сравнение использует одинаковые запросы и **свежий fixed в том же повторе**. Для записей всего диапазона эталон строится независимо через разностный массив с учётом циклов и остатка; затем сравнивается каждый элемент результата. Старые fixed из таблиц с записью одного элемента не служат знаменателем новых измерений.

Основные диагностические поля CSV:

| Поле | Что измеряется |
|---|---|
| `wall_s`, `cpu_s` | Полное время и суммарное CPU-время процесса |
| `rebuild_ms` | Сумма времени всех попыток перестройки, включая снимки и ожидания |
| `optimize_ms` | Оценка старого/нового разбиения и построение кандидата |
| `publication_wait_ms` | Сумма времени от начала остановки admission до захвата всех mutex |
| `publication_hold_ms` | Сумма времени обновления после захвата всех mutex, до их освобождения |
| `max_publication_pause_ms` | Максимальная остановка admission целиком, включая освобождение mutex |
| `last_window_samples` | Число выбранных запросов в последнем окне, дошедшем до оптимизации; **не общий счётчик** |

Эти времена пересекаются: оптимизация и публикация уже входят в `rebuild_ms`, а вся перестройка — в `wall_s`. Их нельзя вычитать из результата или повторно прибавлять. Отношение `rebuild_ms / wall_s` — доля elapsed-времени фоновой работы, а не непосредственная потеря throughput.

## Сравнение с multi-granularity locking

Новый baseline `mgl` — **наша реализация классического протокола IS/IX/S/X**, не авторский artifact другой статьи. Основа — [multi-granularity locking Gray et al.](https://jimgray.azurewebsites.net/papers/Granularity%20of%20Locks%20In%20a%20Large%20Shared%20Databse%20RJ%201606.pdf). Код: [MultiGranularityRangeLock](common/multigranularity_lock.hpp).

Статическое двоичное дерево делит массив на листья. Частично покрытые запросом узлы берут IS для чтения или IX для записи; максимально крупные полностью покрытые узлы — S или X. Все состояния удерживаются до завершения callback, освобождаются в обратном порядке. Общий preorder дерева предотвращает циклы захвата; upgrades нет. SIX для этих одиночных read-only/write-range операций не требуется. Совместимость реализована атомарным 64-битным словом на узел и `atomic::wait/notify`; per-query heap allocation отсутствует. FIFO и starvation-freedom не заявляются.

`--mgl-leaves` задаёт степень двойки (по умолчанию 1024). Запросы округляются до листьев. Это **другая организация и другой бюджет состояний**, а не ещё один вариант с K=64: в измерениях 1024 листа, 2047 узлов, 262016 байт под узлы. В CSV сохранены запрошенные и фактические листья, число узлов и память. Поле `effective_lock_kind=atomic_mgl` отличает native MGL от выбранного для наших реализаций `std::mutex`.

17 ноября выполнены **36 проверенных измерений**: 8 потоков, три повтора, одинаковые запросы внутри каждой четвёрки fixed/balanced/DP/MGL. Диапазонные записи увеличивают каждый элемент; Q=24 млн всего, N=2²⁶, L=10000, B=1024, lambda=10000, проверка перестройки10с. Все затраты и холодный старт включены. [Полная таблица и ограничения](BENCHMARK_RESULT/2026-11-17/mgl_comparison/TABLE.md), [сырые данные](BENCHMARK_RESULT/2026-11-17/mgl_comparison/summary.csv).

| Нагрузка | Balanced / fixed | DP / fixed | MGL / fixed |
|---|---:|---:|---:|
| Постоянное окно | 1,76 | 1,67 | 2,02 |
| Четыре островка | 1,86 | 1,87 | 2,67 |

Здесь **MGL быстрее наших адаптивных вариантов по полному времени**. На постоянном окне разница примерно1,21–1,24×, на островках1,43×. MGL имеет мелкие регионы с начала запуска и использует другие примитивы/больше состояний; этот эксперимент не разделяет вклад этих факторов. Короткий контроль из5млн точек показывает большой overhead иерархии, но не оценивает адаптацию: наши варианты заканчиваются до первой перестройки. При 64 листьях MGL содержит 127 узлов; при 32 — 63 узла. [Сводная таблица всех трёх размеров и сырые данные](BENCHMARK_RESULT/2026-11-17/mgl_budget/TABLE.md).

| Нагрузка | Balanced / MGL64 | DP / MGL64 | Balanced / MGL32 | DP / MGL32 |
|---|---:|---:|---:|---:|
| Постоянное окно | 1,31 | 1,24 | 1,71 | 1,64 |
| Четыре островка | 1,32 | 1,33 | 1,32 | 1,32 |

### Как устроен прежний алгоритм

Массив разбивается максимум на `B = 64 × K` мелких блоков одинакового размера; последний может быть короче. При `K = 64` это максимум 4096 блоков. Блоки каждой группы смежны, одна группа защищена одним мьютексом.

Для выбранных статистикой запросов `q` с включёнными концами в блоках `l(q), r(q)` сохраняется исходный вес блока:

```text
w[i] = Σq 1{l(q) ≤ i ≤ r(q)}
L[g] = Σi∈g w[i]
```

То есть длинный запрос учитывается в **каждом** затронутом мелком блоке. Чтобы не обходить весь диапазон при сборе статистики, запрос увеличивает только счётчики начала и конца. Во время перестройки префиксный проход восстанавливает те же `w[i]`.

Все три стратегии используют эти веса и непрерывные группы:

| Стратегия | Целевая функция | Вычисление |
|---|---|---|
| `DynamicProgramming` — по умолчанию | Минимум `Σg L[g]²` | Точное динамическое программирование с ускорением divide-and-conquer, `O(K B log B)` |
| `Genetic` | Приближённое уменьшение `Σg L[g]²` | 24 кандидата, до 18 поколений; остановка после 4 поколений без улучшения; оценка кандидата `O(K)` |
| `Balanced` | Минимум `max L[g]` | Бинарный поиск допустимой нагрузки, жадная группировка и распределение оставшихся мьютексов, `O(B log W + K B)`, где `W = Σi w[i]` |

После жадной группировки `Balanced` может использовать меньше `K` групп: например, один неделимый тяжёлый блок задаёт большой допустимый максимум. Оставшиеся мьютексы распределяются последовательным выбором разреза с наибольшим уменьшением исходной суммы квадратов нагрузки. Разделение группы не увеличивает её максимальную нагрузку, поэтому оптимум `max L[g]` сохраняется. Так свободные мьютексы помогают нагруженным областям; глобальный минимум суммы квадратов по-прежнему ищет только DP.

Для DP состояние `F(g,j)` — минимальная стоимость покрытия первых `j` блоков `g` группами. Переход выбирает начало последней группы `t`:

```text
F(g,j) = min_t { F(g−1,t) + (prefix[j]−prefix[t])² }
```

Монотонность оптимальной позиции разреза позволяет ускорить поиск, сохранив точный минимум. DP дороже простой балансировки; его затраты могут окупаться за счёт последующих запросов, что и проверяет сравнение полного времени.

Это оптимизация исходных весов, а не модель времени выполнения или точной вероятности конфликтов. Для публикации кандидата во всех стратегиях требуется уменьшение исходной оценки `Σg L[g]²` более чем на 10%. Этот порог подавляет изменения из-за шума выборки; он не означает гарантированное ускорение на 10%.

Перед вычислением кандидата проверяется нижняя граница стоимости: `max(Σi w[i]², (Σi w[i])² / min(K,B))`. Если даже она не даёт нужного улучшения, оптимизатор не запускается. Это исключает заведомо бесполезный расчёт, сохраняя все варианты, которые могли бы пройти порог публикации.

Все три стратегии создают ровно `min(K, B)` непустых групп.

Основные настройки:

| Параметр | Значение по умолчанию | Назначение |
|---|---:|---|
| `K` | 64 в benchmark | Число доступных мьютексов; параметр шаблона |
| Разрешение статистики | до `64 × K` блоков | Компромисс между точностью границ и объёмом статистики |
| `stats_sample_rate` | 64 | Случайная выборка в среднем одного запроса из 64 |
| Интервал перестройки | 30 с (`30000` мс) | Редкая проверка накопленной статистики: примерно два раза в минуту |
| Порог публикации | 10% | Требуемое снижение `Σg L[g]²` |

Малые выборки накапливаются до достаточного числа наблюдений: при 64 мьютексах нужно 640 выбранных запросов. Сбор статистики не использует глобальный счётчик или чтение часов на каждом запросе. Мьютексы в статической и динамической реализациях имеют одинаковое выравнивание.

Для снимка статистики и публикации границ перестройщик временно останавливает новые запросы и захватывает все мьютексы. Само вычисление разбиения выполняется вне этой остановки. Запросы захватывают мьютексы в одном порядке и проверяют версию разбиения, чтобы не выполнить callback с устаревшим набором блокировок.

### API прежнего DynamicLock

```cpp
#include "dynamic/dynamic_lock.hpp"
#include <vector>

std::vector<int> data(1 << 20);
DynamicLock<64> lock(data.size()); // DP; статистика в среднем 1/64 запросов.
lock.StartRebuilder();            // Период 30 с; запуск явный.
lock.WriteQuery(10, 20, [&](size_t left, size_t right) {
    for (size_t i = left; i <= right; ++i) {
        ++data[i];
    }
});
lock.StopRebuilder();
```

`WriteQuery(left, right, callback)` защищает **включённый** диапазон `[left, right]`; точка — `[i, i]`. Концы ограничиваются размером массива и меняются местами, если переданы в обратном порядке. Для пустого массива callback не вызывается. Блокировка не владеет данными: все конкурентные обращения к ним должны соблюдать тот же протокол защиты.

Callback должен закончить работу с защищёнными данными до возврата. Нельзя вызывать из него какие-либо методы того же объекта блокировки или сохранять ссылки для последующего доступа без блокировки. Исключение из callback освобождает захваченные мьютексы.

Третий аргумент конструктора выбирает `PartitionStrategy::DynamicProgramming`, `PartitionStrategy::Balanced` или `PartitionStrategy::Genetic`; второй задаёт частоту выборки. Необязательный четвёртый аргумент — seed генетического поиска (123 по умолчанию). Например: `DynamicLock<64> lock(size, 64, PartitionStrategy::Balanced);`. Все три стратегии используют один и тот же код синхронизации и сбора статистики.

`RebuildNow()` позволяет вызвать перестройку вручную; `StartRebuilder(interval)` и `StopRebuilder()` управляют фоновым потоком, деструктор также останавливает его. `PartitionCuts()` возвращает границы **в координатах элементов массива**, включая `0` и размер массива; сами группы полуоткрытые `[cuts[i], cuts[i+1])`. `CountLocksForRange()` считает мьютексы для включённого диапазона. `GetRebuildCount()` считает опубликованные изменения, а `GetRebuildTimeMs()` — время попыток перестройки, включая ожидания, снимок и публикацию. `GetOptimizationCount()` считает запуски оптимизатора после проверки достаточности выборки и нижней границы стоимости; в benchmark это поле `optimizations`.

### Исторические измерения

### Mutex, spinlock и RW-lock: чтения и записи

`--lock-kind mutex|spinlock|rwlock` выбирает блокировки данных; `--read-percent 0..100` задаёт вероятность запроса только на чтение (по умолчанию 0, как в прежних тестах). `rwlock` использует `std::shared_mutex`: `ReadQuery` захватывает shared/read, `WriteQuery` — exclusive/write. Mutex и spinlock захватываются эксклюзивно и для чтений. Используется прежний spinlock из `common/spinlock.cpp`, с `yield()` при ожидании. Управляющие mutex фонового перестройщика остаются обычными.

Чтение суммирует весь диапазон без изменения данных. Запись читает диапазон и изменяет один элемент. Тип запроса выбирается отдельным генератором, поэтому координаты и длины не зависят от доли чтений. В CSV добавлены `lock_kind`, `read_percent`, `read_operations`, `write_operations`. У адаптивных структур чтения учитываются в статистике: отдельное состояние генератора на поток и атомарные приращения выбранных счётчиков через `atomic_ref`; этот путь одинаков для всех трёх типов блокировок. Снимок статистики и публикация разбиения берут все блокировки эксклюзивно.

12 октября: `steady_range`, 8 потоков, N=2²⁶, H=2²², L=10 000, 24 млн запросов всего, 90% чтений / 10% записей, 64 блокировки, выборка 1/64, проверка перестройки раз в 10 с. Фактически 21 598 051 чтение и 2 401 949 записей; последовательности запросов одинаковые во всех девяти запусках. Один повтор, весь цикл структуры с холодным началом и перестройками включён. Серия завершилась за 189,48 с; все итоговые массивы проверены. Первичный эксперимент на одной нагрузке, а не вывод для любых долей чтения и длин запросов.

| Алгоритм | Mutex, млн запросов/с | Spinlock, млн/с | RW-lock, млн/с | Spinlock / mutex | RW-lock / mutex |
|---|---:|---:|---:|---:|---:|
| fixed | 0,772 | 1,107 | 0,885 | 1,43× | 1,15× |
| balanced | 1,233 | 1,507 | 1,441 | 1,22× | 1,17× |
| DP | 1,233 | 1,452 | 1,310 | 1,18× | 1,06× |

Относительно mutex у того же алгоритма spinlock потратил на 13–22% больше суммарного CPU-времени, RW-lock — на 4–20% меньше.   --sample-rate 64 --trace-size 1048576 --repetitions 1 --seed 1 --csv /tmp/rwlock.csv

### Прежние нагрузки

Дополнительные варианты выбираются через `--implementations global,per_element`: `global` — один `std::mutex` на весь запрос (`NaiveLock<1>`), `per_element` — плотный массив из одного `std::mutex` на элемент (`ElementLock`). Диапазон целиком блокируется по возрастанию индексов на всё время callback. Можно указать любую непустую выборку из `fixed,balanced,dynamic_dp,genetic,global,per_element`; по умолчанию сохранены прежние три реализации. Поэлементный вариант измеряется в серии 20 сентября только на точках. Таблица: [BASELINE_COMPARISON.md](BASELINE_COMPARISON.md); формулы целей: [BALANCED_VS_DP.md](BALANCED_VS_DP.md).

По умолчанию сравниваются три варианта: `fixed` — статические границы, `balanced` — простая адаптивная балансировка, `dynamic_dp` — адаптация через DP. Добавляемый через `--implementations` вариант `genetic` использует генетический поиск границ. Эти четыре варианта используют 64 одинаковых мьютекса и исполняют одни и те же заранее сгенерированные последовательности запросов. Каждый запрос читает **весь** защищённый диапазон, суммирует значения и прибавляет заданную величину к одному элементу внутри него. Для каждого потока и фазы генерируется независимая случайная последовательность; после её исчерпания она повторяется циклически. Выбор горячей области не синхронизирован между потоками.

В `wall_s` включён весь жизненный цикл блокировки: создание, сбор статистики, запуск потоков, ожидания, все перестройки, остановка фонового потока и уничтожение. Предварительного обучения нет: первые 30 секунд до первой попытки перестройки целиком входят в измерение. Генерация запросов, обнуление общего массива и проверка эталона исключены одинаково для всех выбранных вариантов. `cpu_s` учитывает процесс целиком, включая перестройщик. `rebuild_ms` — диагностика уже включённой работы; повторно прибавлять её к `wall_s` нельзя.

На каждом повторении все выбранные варианты получают одинаковый trace и отдельный нулевой массив. Порядок выбранных реализаций циклически меняется между повторениями и сценариями. Эталон учитывает все полные циклы trace и остаток последнего цикла. Итоговый массив сравнивается с ним поэлементно; ошибка завершает программу с ненулевым кодом. Сумма прочитанных значений зависит от порядка выполнения потоков и сама по себе не является проверкой корректности. Она всегда печатается как `read_checksum`, в том числе без CSV, чтобы результат чтения использовался программой; печать выполняется вне измеряемого интервала.

Каждый адаптивный вариант сравнивается с `fixed` того же повторения: ускорение — `fixed.wall_s / variant.wall_s`; меньше единицы означает проигрыш. Вывод содержит медиану **парных** ускорений и их минимум/максимум. CSV сохраняет каждое измерение, параметры, seed, CPU-время, перестройки, границы и времена фаз. `phase_wall_s` помогает увидеть реакцию на смену нагрузки, но не заменяет полное `wall_s`.

```sh
# Быстрая проверка всех сценариев; при 30 с перестройка может не начаться.
./build/paper-release/adaptive_lock_benchmark --model legacy --write-body single --threads 8 --operations 4000000 \
  --repetitions 5 --seed 1 --scenario all --csv suite.csv

# Короткая проверка большого массива и расходов до первой перестройки.
./build/paper-release/adaptive_lock_benchmark --model legacy --write-body single --threads 8 --array-size 67108864 \
  --hot-width 4194304 --range-length 10000 --operations 1000000 \
  --repetitions 5 --seed 1 --scenario steady_range --csv large-hot-range-cold.csv

# Длинные прогоны для редких перестроек: число операций подбирается по wall_s.
./build/paper-release/adaptive_lock_benchmark --model legacy --write-body single --threads 8 --operations 2000000000 \
  --repetitions 5 --seed 1 --scenario shift --rebuild-ms 30000 \
  --trace-size 1048576 --csv rare-hot-point.csv

./build/paper-release/adaptive_lock_benchmark --model legacy --write-body single --threads 8 --array-size 67108864 \
  --hot-width 4194304 --range-length 10000 --operations 60000000 \
  --repetitions 5 --seed 1 --scenario steady_range --rebuild-ms 30000 \
  --trace-size 1048576 --csv rare-large-hot-range.csv

./build/paper-release/adaptive_lock_benchmark --help
```

Для оценки редкой адаптации каждый адаптивный прогон должен включать 30 секунд до первой попытки перестройки и заметный участок работы после неё. Ориентир — 60 секунд и больше, но это не обязательная граница длительности. Числа 2 млрд и 60 млн выше — стартовые настройки, а не обещание длительности: проверьте `wall_s` и `rebuilds`, затем при необходимости увеличьте число операций одинаково для всех вариантов. В `--scenario shift` выполняются две равные по числу операций фазы: слева и справа. Важно, чтобы и отдельные фазы были достаточно длинными; проверяйте `phase_wall_s`. Короткий прогон с `rebuilds=0` показывает расходы до адаптации, но не её пользу.

`--operations` — общее число операций на сценарий для одного варианта, не число операций на поток; по умолчанию 4 млн. `--range-length` задаёт точную длину для `*_range` и верхнюю границу равномерного выбора длины от 1 для `*_variable_range`. Все размеры задаются в элементах; массив benchmark содержит `uint64_t`. Для больших массивов учитывайте также память эталона и trace.

`--trace-size` (по умолчанию 1048576) ограничивает число сохранённых записей запросов **на одну фазу суммарно по всем потокам**. Фактическое число зависит от размера фазы; весь сценарий может хранить до этого лимита, умноженного на число фаз. Это позволяет выполнить миллиарды операций без пропорционального роста памяти. Нагрузка внутри фазы периодическая: повторённая операция берётся из того же trace, а не генерируется заново. У всех выбранных вариантов одинаковые последовательности и условия повторного использования данных trace в кэше. CSV сохраняет настроенный `trace_size` и фактический `unique_queries` по всему сценарию; последнее поле считает записи trace, среди которых случайно могут встретиться одинаковые запросы. Эти параметры нужны для воспроизводимости.

Основу набора составляют 14 сценариев с отдельными сохранёнными измерениями за 14–15 сентября. Дополнительно добавлен `sliding_variable_range` с восемью постепенными сдвигами окна (всего 15 сценариев). Остальные варианты, проходившие только короткий общий прогон, удалены из генератора; их исторические CSV сохранены. Стабильные идентификаторы сценариев сохраняют прежние seed и порядок реализаций после сокращения списка.

| Сценарий | Нагрузка |
|---|---|
| `uniform` | Равномерные точечные запросы по массиву; контроль накладных расходов |
| `clusters_2` | Точечные запросы в двух равновероятных горячих окнах |
| `clusters_8` | Точечные запросы в восьми равновероятных горячих окнах |
| `unequal` | Четыре окна, точечные запросы с долями 70/10/10/10% |
| `clusters_2_range` | Диапазоны заданной длины в двух горячих окнах |
| `clusters_4_range` | Диапазоны заданной длины в четырёх горячих окнах |
| `shift` | Точечные запросы: горячая область слева, затем справа |
| `steady_range` | Диапазоны заданной длины в неизменной горячей области; четыре фазы |
| `hot_with_spike` | 70% точечных запросов внутри окна, 30% в одну точку в его центре |
| `islands_range` | Четыре маленьких острова с холодными промежутками; диапазоны заданной длины |

| `moving_variable_range` | Случайная длина 1…L; окно слева в фазах 1–2, справа в фазах 3–4 |

Параметры `--sample-rate` и `--rebuild-ms` общие для всех выбранных сценариев. `--partitions` дополнительно печатает итоговые границы. При периоде 30 с стандартный короткий запуск на 4 млн операций часто заканчивается до первой перестройки. Он проверяет корректность и начальные расходы, а не выигрыш после адаптации. Интервалы 1–10 мс полезны для проверки механизма и исследовательских запусков, но их результаты не подтверждают эффективность режима с двумя перестройками в минуту. Разрешение мелких блоков, длинные пересекающиеся диапазоны, скорость смены нагрузки и число потоков ограничивают возможное ускорение. Для сравнения производительности запускайте Release без конкурирующих тяжёлых задач и сохраняйте все повторения.

### Сохранённые NUMA-скрипты и прежняя структура

Следующие скрипты сохранены из прежних экспериментов и не входят в новую проверочную серию. Их методику и настройки нужно проверять отдельно; текущий переносимый запуск приведён выше. На Linux с `numactl`, `timeout` и Python 3:

```sh
scripts/numa_build.sh
THREADS=32 NODE=0 scripts/numa_one_node.sh
THREADS=64 NODES=0,1 scripts/numa_two_node.sh
```

Каждый запуск проходит все сценарии с общими настройками. Доступны переменные `OPERATIONS`, `REPETITIONS`, `SEED`, `ARRAY_SIZE`, `HOT_WIDTH`, `RANGE_LENGTH`, `SAMPLE_RATE`, `REBUILD_MS`, `TRACE_SIZE` и `NUMA_TIMEOUT_SECONDS`; по умолчанию NUMA-запуск использует 2 млн операций, 3 повторения и интервал 30 с. Для оценки редких перестроек увеличивайте `OPERATIONS` до нужной длительности и при необходимости общий timeout. `numa_smoke.sh` сокращает весь набор до 100 тыс. операций и одного повторения. Результаты, команда, топология, код завершения и неполные CSV при ошибке сохраняются в `BENCHMARK_RESULT/numa/`. Сводка показывает каждое повторение, включая проигрыши и неудачные запуски.
