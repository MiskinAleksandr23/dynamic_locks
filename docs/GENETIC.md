# Genetic: запуск и упрощение

В основном `adaptive_lock_benchmark` теперь есть `--implementations genetic`.
Он выполняет те же запросы и проверяет тот же итоговый массив, что `fixed`,
`balanced` и `dynamic_dp`. Для всех четырёх вариантов одинаковы 64 мьютекса,
разрешение статистики, sampling и измерение полного времени с холодного старта.

Проверенные прогоны и таблица: [результаты 22 сентября](../BENCHMARK_RESULT/2026-09-22/README.md).
Полная серия на 8 потоках: [времена и сравнение с fixed](../BENCHMARK_RESULT/2026-09-22/FULL_RESULTS.md).
Масштабирование на **4/6/8/10 потоках**: [отдельная таблица genetic](../GENETIC_COMPARISON.md) и [общая таблица](../BENCHMARK_SHORT.md).

```sh
cmake -S . -B build/genetic-release -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_CXX_COMPILER=/opt/homebrew/opt/llvm/bin/clang++
cmake --build build/genetic-release -j 4
ctest --test-dir build/genetic-release --output-on-failure

# Прежние параметры steady_range; проверка перестройки раз в 30 секунд.
./build/genetic-release/adaptive_lock_benchmark \
  --implementations fixed,balanced,dynamic_dp,genetic \
  --scenario steady_range --threads 8 --operations 64000000 --repetitions 1 \
  --array-size 67108864 --hot-width 4194304 --range-length 10000 \
  --rebuild-ms 30000 --sample-rate 64 --seed 1 --csv genetic.csv
```

Путь компилятора выше относится к этой macOS; на другой машине выберите свой
компилятор с библиотекой C++20 и поддержкой `std::jthread`.
`--rebuild-ms 60000` уменьшает частоту проверок до одного раза в минуту.
Короткий прогон может закончиться до первой проверки — смотрите `optimizations`
и `rebuilds`. Интервал отсчитывается после завершения предыдущей проверки;
поиск и публикация входят в полное время. `StopRebuilder()` прерывает ожидание.

Для библиотеки:

```cpp
DynamicLock<64> lock(size, 64, PartitionStrategy::Genetic, 123);
lock.StartRebuilder(std::chrono::seconds(30));
// WriteQuery / StopRebuilder / RebuildNow — общий API DynamicLock.
```

## Что удалось упростить

Прежний код `genetic/genetic_partitioner.hpp` хранит историю запросов и несколько
режимов нагрузки. Перед эволюционным поиском он пытается применить разбиение,
вычисленное квадратичным DP; при успехе генетический поиск вообще не выполняется.
В старом `GeneticLock` каждый запрос читает часы и обновляет общие атомарные
счётчики. `StartRebuilder(interval)` игнорирует interval; ограничение по числу
операций применяется не после каждого успешного изменения границ. Старое demo
содержит всего 1,44 млн online-запросов при начальном probe gap 5 млн, поэтому
этот online-прогон вовсе не обучается.

Новая реализация — [histogram_partitioner.hpp](../genetic/histogram_partitioner.hpp)
и стратегия `Genetic` в общем `DynamicLock`. У неё нет истории запросов,
кластеризации режимов, отдельной очереди обучения или отдельного протокола
синхронизации. Возврат нагрузки обрабатывается следующим поиском по свежей
статистике, без памяти режимов.

- Хромосома — границы непустых смежных групп. Начальные кандидаты: текущее
  разбиение, равномерное и дешёвые квантили нагрузки.
- Fitness — `Σ load²`, как у DP в текущем стенде. Старый штраф
  `5000 × avg_mutexes_per_query` убран; это явное изменение целевой функции.
- Настоящие скрещивание, мутации и отбор: 24 кандидата, 4 элитных,
  максимум 18 поколений. После 4 поколений без улучшения поиск заканчивается.
- Гистограмма и префиксные суммы строятся один раз; кандидат оценивается за
  `O(K)`. DP или Balanced внутри genetic не вызываются. Оптимальность
  результата не гарантируется; текущее разбиение сохраняется среди кандидатов.
- По умолчанию проверка раз в 30 с, выборка примерно 1/64 запросов, минимум
  640 наблюдений при 64 мьютексах. Если нижняя граница стоимости исключает
  улучшение более чем на 10%, поиск пропускается. Публикация требует такого же
  улучшения. Это порог оценки нагрузки, не обещание ускорения на 10%.
- Время запроса не измеряется внутри блокировки; общих счётчиков запросов нет.
  Статистика собирается тем же кодом, что для Balanced и DP.

В выводе `optimizations` — число запусков поиска, `rebuilds` — число применённых
разбиений, `rebuild_ms` — суммарное время всех проверок, включая снимок,
вычисление и публикацию. `rebuild_ms` уже включено в `wall_s`.

## Те же сценарии и воспроизводимость

```sh
# Все 15 сценариев, исходные размеры/геометрия, 3 повтора.
# Укорочено: 20 млн точек или 1 млн диапазонов, интервал 100 мс.
python3 scripts/genetic_compare.py --profile quick --output /tmp/genetic-quick

# Полные прежние объёмы из BENCHMARK_SHORT.md, интервал 30 с, 1 повтор.
python3 scripts/genetic_compare.py --profile full --output /tmp/genetic-full

# Один полный сценарий; также доступны --threads и --binary.
python3 scripts/genetic_compare.py --profile full --scenarios steady_range \
  --output /tmp/genetic-rare

# Только genetic: не повторять DP и Balanced.
python3 scripts/genetic_compare.py --profile full --implementations genetic \
  --threads 8 --output /tmp/genetic-only
```

`--implementations fixed` запускает отдельный контрольный fixed. Для прежнего
`sliding_variable_range`, где использовался интервал 10 с, можно передать
`--scenarios sliding_variable_range --rebuild-ms 10000`.

Скрипт выполняет реализации последовательно, сохраняет точные команды,
хеши исходников/бинарника, CSV и логи; существующий каталог не перезаписывает.
Каждый повтор использует одинаковые запросы для всех реализаций, порядок
запуска меняется. Быстрый профиль проверяет работу адаптации, но не заменяет
полный прогон с редкими перестройками.

Проверки корректности включают весь существующий набор для блокировок:
пустые/малые массивы, диапазоны, исключения, lifecycle, конкурентные записи и
смену границ. Отдельно проверяются интервал, пропуск поиска на стабильной
оптимальной нагрузке, смена и возврат hotspot, допустимость границ, сохранение
лучшего кандидата и воспроизводимость seed. Стоимость genetic сравнивается с
точным DP как нижней границей, без требования найти точный оптимум.

## Прежний отдельный demo

Старые заголовки и API оставлены для совместимости с Benchmark-v700.
`genetic_lock_benchmark` запускает именно прежнюю реализацию:

```sh
cmake -S . -B build/genetic-release -DBUILD_GENETIC_BENCHMARK=ON
cmake --build build/genetic-release --target genetic_lock_benchmark -j 4
./build/genetic-release/genetic_lock_benchmark
```

Его результаты lock/unlock с пустым callback нельзя напрямую сравнивать с
основным стендом, который выполняет чтения всего диапазона и запись.
Для нового сравнения используйте `adaptive_lock_benchmark --implementations genetic`.
